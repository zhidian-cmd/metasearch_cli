## 一、与 Python 参考实现的差异

参考实现：deep_search MCP 的 `search_engine/search_core`（Python 版，2026-09-20 已从该项目移除）

| 未移植项 | 参考实现里的作用 | 为什么不移植 |
|---|---|---|
| RRF 融合排序 | `ranking/reciprocal_rank_fusion.py` | 本 CLI 只做检索 |
| 引擎权重表 / 内容质量分 | `ENGINE_WEIGHTS` / `content_signal.py` | 权重与质量分只服务排序 |
| 广告/垃圾页剔除 | `is_junk_metadata` + 关键词剔除 | **过滤即删结果**，与"宁放过不杀错"冲突（原注释记载旧表曾误杀 12 条中的 7 条正常 URL） |
| 入口层 URL 归一化 | 剥 `www./m./amp.` + 尾斜杠 | **改的是 URL 本身**，属放宽型改写；聚合层不碰（保持"差一个字节就是两条"）。同页判定改由**去重层**只读地进行，见第五节 |
| 引擎自家壳页 | quark `_real_url()` 还原不出直链就丢弃 | 改为**分类处理**：媒体垂直与 `/s/` 中转壳源头剔除；文本聚合壳保留并清洗跟踪参数 |
| 敲门与聚合的关系 | 串行两段 | **重叠**，见 [`perf.md`](perf.md) 与下方第三节 |

聚合层**只按精确 URL 相等合并**，不改 URL 一个字节 —— 差一个字节就是两条，判据逐条可复核。

⚠️ **别把这句话套到去重层**：去重层为了判"是不是同一页"，确实会做尾斜杠归并、query 排序、
剥追踪参数，但**那只用于比较，输出的 URL 仍是原始写法**。两层的分工见第五节。

### 定位：不做 Go-vs-Python 性能对照

本 CLI 是**给 Python 侧调用的检索内核**，不是要取代参考实现。用户原话：
"别在那里乱比较，我只是想解决核心并发慢，之后依然用 python 接到外面。"
**不要为了"显得更好"而做跨实现对照表。**

## 二、"不做"类决策（契约，别翻案）

### 不做排序
用户已否决 RRF 融合 + 引擎权重 + 内容质量分（"权重根本没有用"），
`internal/rank` 整包已删。`results` 按引擎名字母序入池，同引擎内保持其原始排名，**不重排**。

### 条数口径恒定为 15
`-limit` 默认 15（= 参考实现 `text_sources_per_query`）。**不要按需下发条数参数**替上游
"省流量" —— 用户对此有过明确教训。各引擎真实天花板不同（anysearch 官方 10、exa 约 12、
bing 每页约 10、serpapi `num` 被忽略且首页约 10 条、quark 约 11~15）。

### 过滤 = 删结果，一律不做
广告剔除、垃圾页预筛一律不做（`-drop-ads` 已整体删除），用非破坏性方式（`engine_status`、
字段）呈现，由调用方决定。**不要拿"结果条数少了"解释成"我多筛了一层"** —— 逻辑反了。

⚠️ **quark 的 `addition` 标记同样不用于剔除**（用户明确要求）：它是可识别的推广卡标记，
但"用标记删结果"仍是过滤。**维持黑名单过滤现状**：只剔媒体垂直与中转壳。

### 摘要不截断（有意偏离参考实现）

参考实现有 `aggregate.SNIPPET_MAX = 400`，本 CLI **刻意移除了这一截断**（`config.SnippetMax`
已删除，不留常量以免被"顺手"接回去）。理由：

1. **上游正文的流量已经付过**，截断纯粹是让调用方少掉一段可用于精细筛选的依据 ——
   下游要做二次打分/主题相关性判断，400 字不够；
2. 代价（长正文夹带页面噪声、JSON 体积变大）**由调用方自己权衡**，不由本层代劳。

实测代价与收益（2026-09-17，query「跨境电商 政策」）：

| | 截断前 | 截断后（当前） |
|---|---|---|
| 恰好 400 字的条目 | 37 / 87 | **0** |
| exa 摘要长度中位 | 400（全被砍） | **4063**（最长 9801） |
| snippet 字符总量 | ≤ 34,000 | 104,242 |
| JSON 文件 | ~100 KB | **312 KB** |

用户抱怨过"写了太多垃圾文件"。已从 31 文件/10 包压到 **17 个业务文件 + 4 个测试文件 + 2 个取证探针 / 7 包**（合并方向：

例外是**取证探针**（带 `probe` 构建标签，`go build`/`go test ./...` 都看不到）：
`internal/provider/rawdump_probe_test.go`（复刻真实请求，"这个字段到底存不存在"非它不可）、

### 质量指标用「整体率」，**不用**排名加权（2026-09-19 评估后退役）

评估过一套按名次配权的口径（第 1 名权重最大）：

| 口径 | 公式 | 结论 |
|---|---|---|
| 固定 210 | `Σ(21-r)/210` | ❌ 用 20 条的尺子量 10 条的榜单：bing 广告被读成 0.155556（比自身归一低 22%），且**偏差有方向** —— 坏条目靠首屏就低估、靠短榜单队尾就高估（anysearch 唯一那条跑题：11/210 vs 1/55，高估 188%） |
| 上限归一 | 用引擎硬上限当 N | ❌ 对 20 上限的引擎（quark/tavily/…）退化成固定 210，等于没改 |
| 自身归一 | `Σ(N_j+1-r)/(N_j(N_j+1)/2)` | ✅ 数学上最干净（每轮按自己那份榜单归一），但**换不来结论**（见下） |
| 6 轮合并 | 一个大分母 | ❌ 大盘轮次主导：quark 广告被抬成 0.543158（宏平均 0.281063） |

**为什么最终不用**（三条，缺一条都还可能留着）：

1. **没有消费者**。本 CLI 明文「不做排序」「过滤 = 删结果一律不做」，结果整批交给下游；
   下游（模型/脚本）不按名次消费，"第 1 条是广告比第 20 条更坏"这个假设无人兑现。
   这与「只留能兑现的东西」是同一条判据 —— 现存引擎订单靠 `rank` 字段表达就够了。
2. **它挪不动结论**。五个口径下 8 引擎的排序实测（`%TEMP%\msquality\orders.py`）：
   - 跑题率：**五种口径顺序完全一致**（bing ≫ serpapi/tavily/anysearch，其余全 0）；
   - 无效率：只有 anysearch 在固定 210 下被挪一位，其余一致；
   - 广告率：三个"整份榜单"口径只在 tavily/serpapi/quark/anysearch 四个之间互换，
     它们本来就全挤在 0.24~0.40 的带宽里。
3. **它带来三个可调参数**（权重形式 / 分母选择 / 宏平均 vs 合并），每个都能挪动 0.01~0.02 ——
   而判定本身的边界漂移实测就有 ±0.008（同一批数据重标一次，3 个格子各动了 1 条）。
   **口径之争的量级大于样本噪声，等于在噪声上做选择。**

**采用**：

- **主指标 = 整体率**：逐轮 `坏条数 / 实得条数`，再对 6 个关键词**宏平均**（一个关键词一票）。
  口径最短、可人工复算、不含任何权重决策。
- **补充 = 前 5 条坏率**：分母恒 5，顶替排名加权想表达的"首屏污染"，但一句话能说清。
  它给出的增量信息只有两条：`serpapi` 的广告大量在 6 名以后（前5条 0.266667 vs 整体 0.383333），
  `qianfan` / `anysearch` 的广告集中在首屏（0.400000 / 0.366667 高于整体 0.341667 / 0.316667）。
- **位置信息**（无效集中在队尾、广告集中在首屏）用文字记在 `perf.md` 即可，不必合成指标。

> ⚠️ 本节是**评估过程**（四口径逐条对照，看"哪个口径会把结论挪走"）；
> **最终拍板的口径与噪声检验在[第八节](#八质量口径整体率为主top-15-为辅归一不作排名2026-09-19-定案)**。
> 两处结论一致、证据互补：本节答"换口径会不会改变排序"，第八节答"这些差异过不过得了噪声"。
> 看"归一到底用不用"只看第八节即可。

## 三、翻页必须串行（并发已实测证伪，勿改）

三个引擎内部翻页都是 `for` 串行：bing `first=11/21/...`、quark `snum=2..3`（默认，
`-max-pages` 可调）、serpapi `start=0/10`（该引擎 `num` 被忽略、首页约 10 条，
默认会翻一页补足 15 —— 见 [`perf.md`](perf.md) 第五节）。

**曾改成并发翻页，实测反而更慢，已回退。** 用户原话："并发的理想是 max，但实际是
max + 限流惩罚……并发翻页是这次更慢的元凶，改回串行。"理论收益是 `max(各页)`，实际拿到的是
`max + 限流惩罚` —— bing/quark 这类无鉴权网页对短时突发请求有风控，并发只会换来下一轮同 query
直接返回错误页（quark 返回 866~882B 空壳 → 整路 0 条）。`fetchBatch` / `pageBatchSize` 已删。

**不要再以"并发更快"为由改回并发 —— 已实跑证伪过一次。**

### `-max-pages` 只对 quark 生效
`provider.Options.MaxPages` 虽然做成了通用字段，但**当前只有 quark 读它**：
bing 按 `limit` 自算页数（`(limit+9)/10` 封顶 5），serpapi `num` 被忽略、默认翻一页补足 15。
四处帮助文本/注释均已标注（`search.go` / `main.go` / `provider.go` / `aggregate.go`），
**不要再写回"各引擎默认"**。

## 四、quark 路线决策

### 必须走移动站纯 HTTP，不用浏览器
桌面站 `www.quark.cn` 的浏览器渲染实测三处硬伤：并发下 8s 预算只渲染出 626KB 空壳（0 条）；
加大到 20s/30s 预算反而返回 **0 字节**（页面永不 idle，挂到被外部超时杀掉）；单引擎
14.5~16.5s 却产出 0 条。移动站 `m.quark.cn` 是**服务端渲染**的，原始 HTML 就带完整结果卡片，
单引擎 1.4~2.5s / 11~14 条稳定产出。

**桌面站已整体落到登录墙后面**（2026-09-16 实测：`#scs` 0 个、`qk-title-text` 0 次，正文是
"请先登录"），参考实现的 `_real_url()` 因而形同虚设。

### 浏览器 + 滚动路线已实测否决
"用浏览器渲染 + 滚动加载"看着能一次拿到更多结果，实测不可行：

| 方案 | 产出 | 耗时 | 稳定性 |
|---|---|---|---|
| 纯 HTTP 首跳（现方案） | 19~21 标题 / 623KB | **1.5s** | 稳定 |
| 纯 HTTP `snum=2..5` | 每页 1.5~2.0s | 稳定 | 稳定 |
| `DynamicFetcher`（headless chromium） | **0 条**（拿到"请先登录"空壳 288KB） | 7.3~9.6s | — |
| `StealthyFetcher` + 滚动 3 次 | 96 标题 / 539KB（**仅偶发**） | 8.0~10.1s | **4/4 次降级** |

1. **quark 对 headless 浏览器指纹做降级**：`DynamicFetcher` 稳定只拿到需要登录的骨架页
   （`qk-link-wrapper` = 0），`StealthyFetcher` 只有极少数轮次能命中完整内容，连续请求后
   **4/4 全降级**，且耗时反而涨到 10s。**不可依赖**。
2. **滚动本身确实能加载更多**（0→3 次滚动：46→96 标题，饱和在 3 次），但这条路被上面的
   指纹降级堵死；而纯 HTTP 侧用 `snum` 翻页拿到的是**同一批增量**且稳定。

   为了滚动引入 playwright/chromium 会让 exe 从"零依赖"变成"要装浏览器内核"，不划算。

### 敲门不走代理（2026-09-17 验证）
用户曾提"直连敲门 + 代理补敲两轮 + CLI/gui 加代理参数（`127.0.0.1:31181`）"，
但**自己先加了条件"前提是代理是不是真的通过握手更多，是才改"**。实测后**一行代码没改**：

- `127.0.0.1:31181` 是 **DeepSearch 自用的本地 HTTP 代理**（响应头带 `DS-Proxy-Request`），
  **与本机同一网络位置**：不可达域名经它返回 `read fail`（连 CONNECT 响应都没有）→ 出不去。

  （`twitter.com` 一次 OK、同域名下一次 `read-fail`）。代价是最坏 4s 尾巴 + 一堆参数。
- ⚠️ **验证代理可达性的正确方法**：裸 TCP 到代理 → 发 `CONNECT host:443` → 看响应行是否
  `HTTP/1.1 2xx`。**敲门只做 TCP 不做 TLS，CONNECT 200 就是等价物。不要用 curl 测 https** ——
  Git Bash 下 curl 走 `schannel`，会对能通的目标误报失败。

抓取阶段（provider `proxyFor()`）仍读环境变量代理（当前 `127.0.0.1:42656`，WorkBuddy 注入，
**与 31181 不是同一个**），这是既存行为，与敲门无关。

## 五、去重（判据移植自 Python 侧，别再退回原版）

### 为什么会有这一节
本 CLI 曾有一版"保守去重"，只做"剥 tracking 后 URL 精确相等"。实测（2026-09-17，
「紫色面具」74 条真实结果）**它只合得掉 1 条**：`?write`（不在 tracking 表里）、尾斜杠差异、
换子域一律合不上。真正合得掉这些的是一份 Python 侧级联判据（当时住在 `core_search/dedup.py`，
同数据合 3 条），于是把那份判据移植进 `internal/dedup` —— 让**检索内核自己**产出合并后的结果，
下游不必再补一层。

⚠️ **那份 Python 对照实现已于 2026-09-18 按要求归档**（备份在
`%TEMP%/metasearch_cli_dedup_rollback/python_dedup_archive/`，含 `dedup.py` / `run_dedup.py` /
`test_dedup.py` / `verify_parity.py`）。**此后只有 Go 一份实现**，判据事实（Unicode 空白、
`\p{Nd}` 取数、否决链）全部落在 `internal/dedup` 的注释与回归用例里。

⚠️ **`gui_dedup.py` 已于 2026-09-18 一并退役归档**（备份在**同一个**归档目录：
`%TEMP%/metasearch_cli_dedup_rollback/python_dedup_archive/gui_dedup.py.retired_20260918`）。
原因：去重搬进 CLI 后它退化成纯转发，**功能成了 `gui.py` 的子集** —— 搜索→控制台这一件事
两边的输出内容完全等价（`-format` 默认就是 `json`，`gui.py` 传的 `-limit 15` 也等于默认值），
而 `gui.py` 还多出引擎选择与密钥管理。它唯一独有的是状态行那句「合并了几条」，
而该数字在 JSON 的 `dedup` 块里本来就有。**两个入口做同一件事只会让人搞混该开哪个。**

因此 `core_search/` 目录现在只剩四样：`gui.py`（唯一入口）、`metasearch_cli.exe`、
`data/`（历史存档）、`out/`。

**四份真实数据交叉验证（移植当时 Go 与 Python 逐条一致、理由一致）**：

| 数据 | 条数 | 合并 |
|---|---|---|
| raw_ai | 84 | 3 |
| raw_meinv | 83 | 2 |
| raw_meitu | 80 | 0 |
| raw_zisemianju | 74 | 3 |

### 判据是两条腿，缺一不可

**腿一：契约 0 —— 规范化 URL 全等 = 同一页 → 无条件合并。**
文本像不像**不构成**保留理由。实测 pexels 同一页被两个引擎返回、URL 只差一个尾斜杠，
而两套标题相似度只有 0.12 —— 靠"两边文本都得像"永远合不上。
`EscapedPath` 把"明码路径"归一到百分号形态（baike 那条），不需要额外解码头；
再对 `%xx` 做**大小写归一** —— `%e7%b4%ab` 与 `%E7%B4%AB` 是同一页（Python 侧 `unquote`
把两者都解成中文，同样是同一页）。query 则**解码 → 按 (k, v) 排序 → 重新编码**，
于是 `?write` 与 `?write=`、`?q=a+b` 与 `?q=a%20b` 也归为同一页。

⚠️ 路径大小写归一与 query 重编码是 **2026-09-18 对齐 Python 时补的**。补之前 Go 的等价类
比 Python **窄**：同一页的两种转义写法（`%e7` / `%E7`）或两种 query 写法（`a+b` / `a%20b`）
Python 合得掉、Go 合不掉 —— 方向虽是漏杀（不会误杀），但会让"同一份数据两个实现给出两个答案"。

**腿二：否决链 —— 拦住"看着像、其实是两个页面"的候选对。**

⚠️⚠️ **这条最容易被后人当累赘删掉，删了就立刻开始误杀。**
京东首页与品牌页的标题归一后**完全相同**（都是"紫色面具品牌及商品"），路径首段一个是空、
一个是 `brand` —— 只有 `veto:diff_section` 拦得住。同类还有 `veto:cross_site`
（跨注册域转载，标题摘要一字不差）与 `veto:diff_numbers`（同站同栏目但分页 id 不同）。

回归用例 `TestJDFirstPageVsBrandPageMustNotMerge` 就是钉这条的 —— 它失败说明否决链被删了。

### 为什么没有"去重档位"（2026-09-18 删命令行开关 → 2026-09-19 删内部预设）

曾有 `-dedup <档位>`（off / url / conservative / balanced / loose）与 `-dedup-threshold`
两个命令行开关，**已全部从源码删除，`off` 档一并删掉**。理由两条：

1. 这层一旦可关，就有人（尤其是**被包成 MCP 之后**）在调用时"顺手"关掉或调松 ——
   于是去重变成可有可无，出了重复还看不出是谁关的（踩过：调用方传了关掉的档，
   输出里 `mode:"off"`，被当成"去重没生效"的证据）。
2. 本 CLI 的接口契约是**调用方只给关键词**，其余全部走流水线，不提供旁路旋钮。

现状：去重**恒开**，判据强度固定为 `dedup.preset` 那一组数字，**没有任何外部入口**
可以改；跨注册域**永不合并**，没有开关能打开它。**conservative 是刻意的**：
删错丢的是一条真结果且不易察觉，漏杀只是多几条。

⚠️ **2026-09-19 起，连"内部预设"也不留了**：`url` / `balanced` / `loose` 三档、
`ParseMode`、`AllModes`、以及 `Preset.AllowCrossSite` 全部删除 —— 它们只有带 `probe`
标签的离线探针能选中，留着就是一条**没人走的旁路**（用户 2026-09-19 的裁决是"都砍"）。
`dedup.mode` 字段仍在输出里（恒为 `conservative`），保留它是为了能一眼看出"去重跑没跑"。
日后真要调松/收紧，改 `internal/dedup/dedup.go` 的 `preset` 一处即可 ——
改前先看下一节「余量实测：阈值是宽平台」，那里有"松到什么程度也基本不多合"的实测。

### 输出了什么、为什么
- `merged_from`：**备用 URL 字典** —— 键是被吞并的那条 URL，值是它的标题、**它自己的**来源引擎
  与判定理由。用字典而非数组：URL 本身就是天然主键。被删的条目**只是降级为备用**、不是无声
  消失 —— 合并掉的是**另一个 URL**（对调用方可能是更好的入口），这正是"保守档删错一条也不致命"
  的兜底。
- `dedup.veto` / `dedup.pass` 计数：直接回答"为什么 92 条只合了 5 条"。否决多说明判据在拦**而不是没跑**
  —— 少了这两个计数，"到底跑没跑"就只能靠猜（踩过：上一版把上游 `mode:"off"` 原样带出来，
  被当成"去重没生效"的证据）。
- `dedup.raw → final` 与 `reachability.dropped_items` **分开记**：前者是去重减量，后者是敲门剔除。
  混在一起就分不清是哪一层在删东西。

### 判据硬事实（曾与 Python 侧逐码点/逐条对齐后确认，结论仍然有效）

对照实现已归档（见上），但**这些事实不许随归档件一起消失**，故全部落到注释与回归用例上：
`TestNormTextStripsUnicodeSpaces` / `TestNumReCoversFullwidthDigits` /
`TestJDFirstPageVsBrandPageMustNotMerge` / `TestTrackingStripsSrsltid` —— 改判据前先看这四条。

- **文本噪声必须吃 Unicode 空白**：`&nbsp;`(U+00A0)、全角空格(U+3000)、U+2002~U+200A 等。
  只认 ASCII 空白会少 23 个字符 —— 同一页被两个引擎分别给出 `&nbsp;` 与普通空格，就判成两页。
- **数字取数用 `\p{Nd}` 而非 `\d`**：Go 的 `\d` 只是 ASCII `[0-9]`，Unicode 的 Nd 类含全角
  `０-９`。退化成 `\d` 时"２０２４"这类数字取不到，数字否决闸会漏判（该拦的没拦）。
- **URL 归一要吃两种转义写法**：`%e7` 与 `%E7` 是同一字节；query **解码 → 按 (k,v) 排序 →
  重新编码**，于是 `?write` 与 `?write=`、`?q=a+b` 与 `?q=a%20b` 也是同一页。
- **验证方法（可复跑、不联网）**：
  `DEDUP_PROBE_JSON=<结果.json> go test -tags probe -run TestProbeRealData -v ./internal/dedup/`
  —— 报档位、进出条数、两阶段减量、否决/通过计数、合并明细（含备用 URL 的标题/引擎/理由）与判据耗时。
  ⚠️ **口径**：CLI 已恒开去重，新产出的 JSON 都是"已去重"的 —— 拿它再跑会**低估**合并量
  （被吞的条目已不在 `results` 里，清 `merged_from` 也救不回来）。要复现历史基线，用开关还在时
  留下的存档 `core_search/data/raw_*.json`（其信封 `mode` 仍是 `off`，即未去重的原始结果）。

**方向安全的已知差异**（Go 的等价类只可能**更宽 → 只会多合、不会少合**）：
- 规范化 URL **不含 scheme** → `http://x/a` 与 `https://x/a` 合并；
- `%2f` 大小写归一 → `%2f` 与 `%2F` 本就是同一个字节，合并正确。

### 边界情况：已拍板维持合并（2026-09-18）

quark 文档预览页 `vt.quark.cn/blm/quark-doc-ssr-*/preview?id=…` 里，**doc_id 不同、标题一字不差**
的两条（「空气炸锅 食谱 大全」里「空气炸锅电子食谱」×2、「空气炸锅美食大全」×2）会被
`d1:title_exact` 分桶、`url+title_high` 判决合并。

**用户拍板：维持合并。** 理由：一份电子食谱挂多个 doc_id，内容极可能高度雷同；
且即便真的不是同一份，被删的那条**已经降级为备用 URL**（连同它自己的标题与命中引擎写在
保留条的 `merged_from` 里），随时可回取 —— **删错不丢信息**，所以不值得为它放松偏置。

要收紧的话方向是"契约 0 之外还须标题与摘要双达标"，代价是多留几条同页，**目前不做**。

### 余量实测：阈值是宽平台，**别再调它**（2026-09-18）

有人会问"去重与免误杀的平衡是不是到头了、还能不能更准"。**用数据回答，别用感觉**：
拿 6 份真实结果共 **504 条**，对每个候选对算「该走哪条路径 + 该路径的最小超出量」（= 余量），
对被放过的对算「离通过还差多少」（= 近失）。

| 实测项 | 结果 |
|---|---|
| 合并 18 条 | **9 条是契约 0**（URL 全等，根本不碰阈值）+ 9 条靠相似度判决 |
| 9 条相似度判决的余量 | `0.100×5 / 0.044 / 0.031 / 0.017 / 0.011`（薄的 4 条已逐条核，全部可辩护） |
| 近失候选对（离通过 <0.15） | **只有 2 对，且两条都是"该合没合"**，没有一条"差点误杀" |
| 阈值从 conservative 松到 loose（0.90→0.80） | 504 条**合计只多合 1 条**，balanced 与 loose 结果还相同（loose/balanced 档已于 2026-09-19 删除，此表是当时的实测） |

结论：**这不是刀尖，是宽平台** —— 旋钮基本是死的，继续调阈值没有收益。真正还缺的是
**索引层的覆盖**（哪些"同一页的不同写法"根本没进候选集），而不是判决层的松紧。

⚠️ 同时提醒：**"0 误杀"是人工逐条判出来的，验证样本只有约 20 次判决**。别把它说成
"算法已证明正确"；新内容类型（商店列表页、PDF 预览、论坛分页）并没有进过样本。

### 跟踪参数表：`srsltid` 是实测漏杀，已补（2026-09-18）

`internal/config` 的 `minimalTracking` 补入 **`srsltid`**（Google 购物的广告点击 id，
与已在表的 `gclid`/`msclkid`/`yclid` 同类）。补之前 `…/x?srsltid=…` 与 `…/x`
**规范化后不相等** → 走不到契约 0；落到相似度层后 URL 相似度仅 0.409（长 token 稀释了
n-gram），又被 `veto:diff_numbers` 先拦下（token 里的数字把数字集合撑大，重合度掉到 0.273
< 0.30）→ **同一页判成两条**。实测 3 对：`openshop.com.hk` / `keychron.com.tw` /
`philips-da.com.tw`。

修的是**索引层**，没有动任何阈值：补入后 3 对全走 `d1:url_exact` 无条件合并。
6 份数据合并数 **18 → 21**（`raw_kb` 2→4、`raw_af` 8→9），**逐条核对新增的只有这 3 对、
零牵连**。钉子：`TestTrackingStripsSrsltid`（含反向断言 —— 参数必须真在表里，
否则将来被"清理冗余"删掉时可能因别的路径碰巧通过而**静默失效**）。

⚠️ 加参数属**放宽**动作，每个新参数都要单独确认是"纯跟踪、不决定内容"，别成批塞
（`?page=2`、`?id=` 这类是有语义的）。

### 永久边界：跨站永不合并（**不是待办**）

`allow_cross_site` 恒为 false —— 不同注册域的一律不合并。本批 14 对跨站候选里，
约 3 对确实是同一篇文章被转载（澎湃 vs 百家号标题一字不差、taptap vs 什么值得买、
大塔手游网 vs 扬子），其余是"同词条不同站"（词典站）与"同主题不同页"（百科类）。
**这是"漏杀保险"本身，不是可优化的缺口** —— 别为了少几条重复去放开它。
含义要说清：**重复永远清不干净**，跨站转载一定会留在结果里。

### 抽检口径：把"信任"换成成本

被吞并的 URL 全在 `merged_from`（键 = URL，值 = `{title, engine, reason}`），删的是**可见性**
不是数据。真正的风险不是"删错"，而是"删错了不知道"。所以每轮只需看极少几条：

| `merged_from` 里的理由 | 是否要人工复核 |
|---|---|
| 含 `d1:url_exact`（约占一半） | **不用看**，URL 全等无争议 |
| 相似度判决、余量 ≥ 0.05 | 基本可放过 |
| 相似度判决、余量 < 0.05 | **这才是要看的那几条**（504 条样本里只有 4 条） |

⚠️ 余量目前只在离线探针里可见，JSON 里只有理由字符串 —— 想让它出现在输出里要先问用户
（**不许自作主张加字段**）。

## 六、代码约定

- **单引擎失败必须隔离**，绝不让一个引擎拖垮整轮（`aggregate.Collect` 的 goroutine 模型）。
- **`-concurrency<=0` = 不限并发**，信号量容量必须取 `len(engines)`。早期写成
  `max(1, 0) = 1`，把 8 个引擎压成**串行**，慢引擎逐个吃掉全局预算，整轮从 20s 劣化到 65s ——
  这个坑读代码看不出来，只有实测计时才暴露。
- **端口按 scheme 取**：一律探 443 会把只提供 80 的 http 站点误判为不可达。
- **诊断信息要结构化进 JSON**（`engine_status` / `reachability`），不要只打日志。
- **合并不丢信息**：引擎并集、各引擎最靠前排名、更长标题摘要、首个非空日期。
- **参数解析用标准库 `flag` + 一层重排**（`main.go` 的 `parseFlags`），支持"关键词与参数任意
  混排"。**不要换回自研解析器。**
- **有意偏离参考实现处，必须在代码注释和文档写清"为什么"**，否则后人会当 bug"修回去"。
- **不留只有测试/探针能走到的分支**，也不留"恒不触发"的死配置（2026-09-19 清理的判据，
  见「只留能兑现的东西」）。要保留，理由必须能兑现成**调用方或实测**。

### 容易踩的实现细节

**quark 的两处 DOM 事实（不这么写就取错）**：

| 事实 | 后果 |
|---|---|
| 标题与摘要在**两个并列的 `<a.qk-link-wrapper>`** 中，不是父子关系 | 只在标题所在 `<a>` 内找 `.qk-paragraph-text` → 11 条里 7 条摘要为空。正确做法：以标题 `<a>` 为锚**向后遍历兄弟节点**（撞到下一条结果的标题就停，防串条）取最长正文；找不到再向上找祖先；最后兜底用锚自身 → 11/11 有摘要 |
| `data-openpageurl` 混着外部站点 / 聚合壳 / 媒体页 / 中转壳四类 | 照单全收会把图片视频页、百科、文档预览器、神马中转页混进结果 → 按上表分类处理 |

**⚠️ 媒体页 / 无正文卡片判定必须覆盖三个位置**（2026-09-16 修过两个真实漏网）：

`isQuarkMedia` 早期版本第一道就是 `host != m.quark.cn → return false`，于是两个都漏了：

| 漏网 | URL 形态 | 现在的判据 |
|---|---|---|
| ① 神马域视频页 | `page.sm.cn/blm/video-page-710/video?h=www.bilibili.com&id=26_*` | 路径标识（`video-page`/`image-page`/…）**或** `h=` 指向视频站（含夸克自家 `user_auth_video`） |
| ② 夸克字词卡片页 | `p.quark.cn/<hash>/char?entity=猫&force_uc_biz_str=1&content_id=...` | 末段路径为 `char`/`word`，**或**带 `entity=` 参数 |

`m.quark.cn` 侧则看 `/vsearch` 前缀与 `qtab=picture|video|image`。

策略是**按类型剔除、未知类型保留** —— 这两处都是混合域，不能一刀切整个域：

- `page.sm.cn/blm/`：文本聚合页（`midpage-*`）**必须留**；
- `p.quark.cn`：`char`/`word` 卡片剔掉，但 `baike.quark.cn/baike?id=*` 是真百科内容，**必须留**。

测试见 `internal/provider/quark_test.go`，含用户贴出的两条真实 URL 作为回归用例。

**⚠️ 摘要里的 markdown 噪声会被清洗**（2026-09-16 新增 `cleanSnippet`）：
`exa`（1/39）、`tavily`（1/37）的摘要会混进正文图片，典型形态
`...交流发言。\n!\n[](./W020231010319517399.png)\n会后，...`。

`cleanSnippet` 把 `![alt](url)` 整段删掉、把 `[text](url)` 降级为 `text`，再做空白归一。
**这是文本清洗，不是过滤** —— 不删结果、不改 URL，与"过滤 = 删结果，一律不做"的契约不冲突。
（另注：用户看到的 `![](...)` 曾被误认成 quark 的问题，实测来源不是 quark。）

**⚠️ exa 的 snippet 会有编码乱码，`repairMojibake` 只做「无损可逆修复」**（2026-09-17 新增）：

*现象*：exa 的 `contents.text`（→ 我们的 `snippet`）偶尔返回 `ç°è±¡çº§ççº¢` 这类字符。

*定位过程（直连 api.exa.ai 复现，不靠推测）*：

| 字段 | 乱码率 |
|---|---|
| `title` | **0.00（5/5 全正常）** |
| `text` | 0.84 / 0.83（5 条里 2 条几乎整段坏） |

**同一份响应里 title 好、text 坏 → 是上游对 `contents.text` 的编码处理有缺陷**，
不是本 CLI 解码错（若我们解码错，title 会一起坏）。全引擎扫描（同 query）确认
**只有 exa 中招**，其余 7 引擎 `maxS ≤ 0.07`。

*修复口径（保守可逆，与"宁放过不杀错"同构）*：
1. 只接受**无损往返**：字符全在 Latin-1 区间 → 映射回字节 → 必须是**合法 UTF-8**
   → 才采用解码结果。
2. 任一步失败（出现 U+FFFD、或 `utf8.Valid` 判假）→ **原样返回**，绝不用替换符凑字。
3. **不做部分修复**。实测 exa 存在**真丢字节**的样本（`â uu` 处少了 `0xC3`，
   字节流 `...e7 e7...` 两个前导字节相连）—— 这种直接解码必失败，按第 2 条保留原文。
4. 修复是**恒等或改正**：不删结果、不改 URL、不动 title、不改条数。

*实测效果*（query「福建兄妹」）：exa 10 条里 9 条修复成功，剩 1 条是不可逆的丢字节样本
（原样保留）。同轮其它 7 引擎 `maxS` 全 ≤0.06，**零误伤**；总条数 71 未因修复减少。

*踩过的坑（写下来免得再犯）*：
- 一开始用"高字节占多数"当判据 → **混排文本**（`abc <乱码> xyz`）被漏掉，
  因为 ASCII 占多数。改成**存在性判据**：存在合法的多字节 UTF-8 序列即可。
- 一开始写了"把解码结果再展开回 Latin-1 比对"当无损证明 → **逻辑反了**：
  解码后是中文（>0xFF），那个比对必然失败，等于永远不修复。
  正确的无损证明就是 `utf8.Valid(buf)` 本身（无替换符、无非法序列）。

测试见 `internal/provider/mojibake_test.go`，含**必须原样返回**的负例
（含 U+FFFD 的、非 Latin-1 的、真丢字节的 exa 样本）。

**壳页 URL 清洗只对 quark 自家聚合壳生效，外部站点一个字节不动**：剥掉
`uc_param_str` / `uc_biz_str` / `docexpbucketstr` / `bucket` / `from` 等纯埋点与实验分桶参数
后，百科页 URL 从 200+ 字符缩到 40 字符左右（实测剥后 HTTP 200、正文长度一致）。
`q` / `title` / `doc_title` **不剥** —— 这两类页面是客户端渲染的，它们是 JS 的输入参数，
剥了可能渲染不出来，200 证明不了"渲染得出来"。

**bing 翻页需要 cookie**：不带 `Cookie: _EDGE_V=1` 时 `first` 被忽略（p1 与 p2 结果
100% 重叠）；带上后翻页生效（p1∩p2=0%）。移动 UA 反而返回 0 条，故坚持桌面 UA。
⚠️ 别因"旧注释说 `first` 被忽略"改回单页 —— 那是**没带 cookie** 时的假象。

**改 usage 原始字符串（反引号 literal）时不要在内部再写反引号** —— 会提前终止 literal 导致
`operator - not defined on \`...\`` 这类诡异编译错（踩过两次）。

- **不要把未验证的归因写进注释 / README / 回复，当结论用。**
  反面案例：`serpapi 32.5s` → 我归因"翻 3 页" → 推出"重试会放大到 60s" → 据此改 `attempts`
  → 用确定语气写成"已解决"。实际三次探针**全 `err=nil`、从未触发重试**，后两步是空中楼阁。
  用户质问"直接打包票说解决了吗"，我认了却仍在注释留确定性措辞 —— 又被打回。
- **改参数前先问：这个分支在默认路径下真的会被执行吗？** 本项目已踩两次
  （serpapi 一堆死配置；此前还有若干"看着有用"的旋钮）。凡触发不到的分支，
  注释里要**显式标注"默认路径永不执行"**，不要让它看起来在起作用。
- **描述代码行为时，要区分"参数设 N 就发 N 次"与"首页就凑满所以只发一次"** ——
  这两句对行为的判断完全不同，写错等于误导后人。
- **没有实测就不要说"解决"**。可以说"改了 X，理由是 Y，但未验证"。
- **用户提"要不要这样改"时，先验他给的前提，前提不成立就不改** —— 正面案例（2026-09-17）：
  用户提代理补敲方案，但自己先加了"前提是代理真的能握手更多，是才改"的条件。实测前提不成立
  → **一行代码没改**。**先花几个探针把前提打掉，比改完再回退省事得多。**
- ⚠️ **评价方案时只统计"实际会走的那条路径"的收益。** 我曾在代理方案里列

  那条路径**永不执行**，拿它减分是给自己加戏、也不相关。**已收回该论点。**

## 八、质量口径：整体率为主、Top-15 为辅，归一不作排名（2026-09-19 定案）

*背景*：给 8 引擎测了广告率 / 跑题率 / 无效率后，又想加"按名次加权"的口径，
在"固定 210 分母"和"自身归一"之间来回改了两次。**用户第三次质疑"总感觉归一没有价值"** ——
不猜了，直接量：算噪声地板、逐对审翻转、做方差分解。结论是用户对了。

**拍板的口径**（整体率与排名加权率的公式与判定表见 [`ranking.md`](ranking.md)；逐轮数据在 `docs/perf.md` §八；
四个候选口径的逐条对照与"评估后退役"的过程见第一节末）

- **主口径 = 整体率**：每轮 `坏条数 / N_j`，再对 6 轮取平均。是"率"，可解释、可复现。
- **第二列 = Top-15 坏率**：`坏条数(rank ≤ 15) / min(N_j, 15)`。选 15 不是随手挑的 ——
  聚合层**每引擎入池就是 15 条**，这是唯一与代码真实行为对齐的口径。
- **自身归一 / 固定 210 都不作排名口径**，只留在表里当对照证据。
- **归一降为诊断量**：只在两引擎 Top-15 率**相等**时，才回头看谁的坏结果更靠前。

**为什么归一不留（都是实测数，不是偏好）**

1. **翻转审计 23 处、显著 0 处**。整体率 vs 前15、整体率 vs 自身归一，6 组对照逐对查，
   翻转对的差值从 0.006676 到 0.041667，**全都小于 2×SE**。归一挪动的每一个位次，
   都是本来就分不开的位次。
2. **固定 210 有个隐含错误假设**："没吐出来的那几条 = 干净的"。于是坏条目靠首屏被低估、
   靠队尾反而**高估 188%**（同一家引擎、同一批数据，一个指标低估一个高估）。
3. **它回答的问题在样本量下测不出来**。"坏结果排多前"是**榜单内**属性，但榜单形状本身
   被 query 类型主导 —— 广告率里 SS_query 占 **83.2%**、SS_engine 只占 **2.1%**。

**顺带推翻的一件事：广告率不能用来选引擎**

引擎间极差 0.166667，**小于**噪声地板 2×SE = 0.336320；关键词间极差 0.898611 是它的 **5.39 倍**
（「空气炸锅 推荐」8 引擎平均 0.923611，「量子计算 进展」0.025000）。
**"哪家广告少"是伪问题。** 要问的是"谁在什么类型的 query 上会崩" ——
唯一过得了噪声检验的答案是 `bing`：跑题 0.375758，是次高 `serpapi` 的 **5.9 倍**，
6 轮里 2 轮整轮切词切歪。

**样本量纪律**（与第七节同源，写下来免得再犯）

- 抽样单元是**关键词**不是条目。同一引擎的广告率跨 6 轮能从 0.000 跳到 1.000，
  所以广告率 SE 中位数 **0.168**，不是 `1/120 ≈ 0.008` 那种量级。
- 任何"A 比 B 好"的说法，先过一遍 2×SE；过不了就写"未分辨"，别写排序。
- 跑题率 SE 只有 0.016667（多数引擎恒 0）、极差 0.383333 —— **这才是能用的指标**。
